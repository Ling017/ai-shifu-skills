# 阶段作战手册

用于把阶段判断转成明确动作、完成标准和补救动作。

| 阶段 | 目标 | 完成标准 | 卡住时怎么办 | 下一阶段触发条件 |
|---|---|---|---|---|
| 初次接触 | 让用户回复并获得基础信息 | 用户说明身份/需求/资料，或选择一个选项 | 给 4 个选项降低回复门槛，不发长文档 | 用户表达需求 |
| 需求判断 | 选择需求价值路径 | 客群 + 需求 tags are clear | 问一个具体场景问题 | 用户同意尝试或询问怎么做 |
| 首课体验 | 让用户自己开始真实资料流程 | 用户已注册、拿到 WorkBuddy/Skill 安装文档，并选定 5-10 分钟小材料 | 给最小资料选择：一个章节、一段 SOP、一个高频问题、一页讲义或一道错题；强调不需要技术、不要代做 | 用户安装 Skill 或开始生成 |
| Skill/生成 | 用户自己生成第一版课程草稿 | 用户已亲自基于真实小材料生成课程草稿 | 缩小范围，不追求完美；卡住时看截图排障，不接手代做 | 用户可以上传或预览 |
| 发布验证 | 拿到学习地址并对齐使用场景 | 用户发来可打开的学习地址，并说明自己体验后的感受 | 发送发布说明，或升级技术排障；发布后不要反复催改课，要转向价值确认 | 学习地址可以正常打开，用户表达认可/不满意/用途 |
| 价值确认 | 结合已产出课程确认价值 | 用户能说出课程适合的对象、用途和下一步使用场景 | 如果用户觉得不完美，说明第一版不完美正常，避免无限打磨；轻问正式使用场景 | 用户认可形式、准备继续使用、询问套餐或有明确交付计划 |
| 案例/示例验证 | 用更低成本验证学习效果 | 用户已看客户案例/示例课，并能说出自己的产品/课程可以怎么做 | 发送案例/示例课，并询问哪部分对应用户场景 | 用户认可价值或询问套餐/采购 |
| 套餐判断 | 推荐套餐方向 | 需求、预计学习人数、课程数量、采购需求已明确 | 只问缺失的套餐判断问题 | 用户接受套餐路径或询问购买细节 |
| 成交收口 | 拿到付款/采购下一步 | 后台套餐付款页、采购负责人、时间线或演示已确定 | 使用异议处理手册；需要授权时升级 | 已付款或正式采购启动 |
| 客户成功 | 产出使用结果 | 7 天内第一门正式课上线 | 如果没有负责人或资料，升级处理 | 出现第二门课、使用扩展或案例信号 |

## 阶段推进强度

- 初次接触/需求判断：轻推进，降低回复门槛。
- 首课体验/发布验证：强推进，目标明确到时间点；体验动作必须是用户自己做出 5-10 分钟样例。
- 价值确认：围绕用户已产出的课程对齐需求，不要让用户陷入不断改课/做新课；目标是确认“产品可以、用户可以、方向成立”。
- 案例/示例验证：证据推进，用已验证案例和示例课降低用户自己找人试学的复杂度。
- 套餐判断/成交收口：明确报价方向、采购动作和截止时间。
- 客户成功：服务推进，防止买完不用。

## 补救动作

| 问题 | 补救动作 |
|---|---|
| 用户没有资料 | 让用户自己选一段反复讲解的内容、一个高频问题、一页大纲、一页讲义、一道错题或一段 SOP |
| 用户说没时间 | 建议自己做 5-10 分钟小样例：只用一个章节或一个高频问题 |
| 用户担心做出来不好 | 把第一版定位为诊断稿，不是最终课程 |
| 用户要求我们帮他做 | 礼貌拒绝代做，解释只有亲自操作才能感受课程创作流程；提供安装文档、排障和生成后点评 |
| 用户已生成但未发布 | 说明生成不是证明，发布学习地址才是证明 |
| 用户已发布但觉得不够好 | 肯定已跑通闭环，说明不完美正常；只建议看 1-2 个关键体验点，不推动反复打磨；转问用途和正式使用计划 |
| 用户认可形式但还在自体验 | 轻问下一步用途：自己验证、给学员体验、招生体验课、系列课；温和说明付费后有更多打磨空间和服务支持 |
| 用户仍然想象不到效果 | 发送个性化学习示例课，再问哪部分可以映射到自己的产品/课程 |
